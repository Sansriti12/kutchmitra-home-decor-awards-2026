## 4. DASHBOARD INFORMATION ARCHITECTURE
--------------------------------------------------

The dashboard should have a clear hierarchy:

A. Applicant identity/header
B. Primary "Start New Nomination" CTA
C. KPI/status summary
D. Draft nominations
E. Submitted nominations
F. Notifications / action required
G. Profile summary
H. Help & support

The applicant should immediately understand:

1. Who am I logged in as?
2. Do I have a draft?
3. Do I have a submitted nomination?
4. What action do I need to take?
5. What is the current status?
6. Where do I continue my nomination?
7. How do I view my submitted dossier?
8. How do I edit my profile?

Do not overload the screen with unnecessary cards.

## 5. START NEW NOMINATION
--------------------------------------------------

Verify that:

Do not create a duplicate nomination flow.

Do not create mock applications.

## 6. DRAFT NOMINATIONS
--------------------------------------------------

- Category
- Project name if available
- Nomination/Draft ID
- Location if available
- Current step

- Last modified time
- Continue Nomination CTA

- Nomination ID
- Category

- Location

Do not invent new award statuses.

Use only statuses already represented in the database/application workflow.

## 15. SECURITY / APPLICANT ISOLATION
--------------------------------------------------

This is mandatory.

Verify:

- Dashboard requires authentication
- Applicant only sees their own profile

- Applicant only sees their own notifications
- Submitted applications remain read-only
- Changing application IDs cannot expose another applicant's application

- RLS remains enforced
- No service-role key reaches client components
- No sensitive database credentials are exposed

DO NOT weaken or bypass RLS.

DO NOT add service-role access to client components.

If a security issue is found, fix it using the existing secure architecture.
